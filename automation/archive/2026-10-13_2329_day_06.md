# How B-Tree Indexes Speed Up SQL Queries 1000x
> **Track:** Database Engineering | **Day:** Saturday | **Date:** 2026-10-13

**Stop table scans: how databases locate rows in milliseconds**

## 📌 Overview
Without an index, the database executes a Full Table Scan O(N), checking millions of rows. A B-Tree index acts like a book index, finding targets in logarithmic O(log N) disk reads.

## 💡 Key Highlights
- Structure: Self-balancing multi-way search tree where leaf nodes form a doubly linked list.
- Clustered vs Non-Clustered: Clustered determines physical row storage order (Primary Key). Non-clustered stores indexed columns with pointers to the data rows.
- Composite Index: An index on (user_id, created_at) must follow the Leftmost Prefix Rule to be utilized.
- Trade-off: Speeds up SELECT queries, but adds write overhead on INSERT, UPDATE, and DELETE because the index tree must rebalance.

## 💻 Code Example
```sql
-- 1. Slow without index (Full Table Scan)
EXPLAIN SELECT * FROM orders WHERE customer_id = 4591;

-- 2. Create B-Tree index
CREATE INDEX idx_orders_customer ON orders(customer_id);

-- 3. Now executes Index Seek in O(log N)
EXPLAIN SELECT * FROM orders WHERE customer_id = 4591;
```

## ⚡ Complexity & Performance
- **Lookup Time:** `O(log N) - typically 3 to 4 disk I/O operations`
- **Storage:** `Consumes 10% - 30% additional disk space per table`

## 🎯 Interview Tip
> [!TIP]
> Be prepared to explain when NOT to use an index: small tables (<1000 rows), frequently written/updated columns with rare reads, or columns with low cardinality (like boolean flags).
